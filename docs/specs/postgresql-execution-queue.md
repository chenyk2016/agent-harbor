# PostgreSQL 执行队列与故障恢复

2026-11-06。源码基线 `f6bee78`。本文定义首版契约和故障实验。队列原型只运行在隔离测试库，生产路径仍待接入。

## 目标

HTTP 返回 202 后，用户可查到原任务。服务在接单、领取或执行过程中崩溃时，恢复能说明这次任务是尚未开始、可以安全接手，还是可能已经产生副作用、需要核对。用户刷新或重试提交不增加模型调用。旧执行器停止得到确认后，下一位执行器才可写同一工作区。

首版按单 Linux 主机、同一 Docker 引擎和每会话一个写入者设计。沿用原生 Claude SDK、会话文件、消息和 SSE 游标。原型使用现有 `messages` 行作为队列项，避免出现一份用户消息和一份必须另外同步的任务。首批只切换普通对话，开发应用与问数仍走既有路径，直到调用方的等待、取消和恢复也能独立于原服务进程。

## 接单到结束

| 阶段 | 持久状态和操作 | 断点恢复 |
| --- | --- | --- |
| 接单 | 鉴权、检查额度和排队上限。在 `ServiceStore.accept` 的现有事务内保存消息、队列归属及 `message.accepted` 事件。以 `sessionId + clientMessageId` 去重。同 ID 参数不一致返回冲突。事务提交后才回 202。 | 响应丢失后用同 ID 重试，返回原任务。未提交事务由 PostgreSQL 回滚。 |
| 领取 | 使用短事务和 `FOR UPDATE SKIP LOCKED` 领取已排队消息。记录执行器 ID、递增执行代次、数据库时间计算的租约。把排队数与运行槽分开，预先限制每用户及全局积压。 | 领取后、派发前崩溃，且旧写入者已确认停止时，可以重新领取。不能把旧版本遗留的 `accepted` 直接当新队列项。 |
| 授权派发 | 取得会话文件锁并核对同一引擎的归属容器。确认旧环境已经停止后，持有会话锁。按当前代次及取消状态原子写入派发标记和状态，再把本轮交给 SDK。 | 派发标记已提交时，记录只能证明“可能已派发”。包括提交标记后、真正发送前的崩溃窗口，都走待核对分支。 |
| 取消 | 排队中直接标记取消。已领取但未派发时，持久化取消意图阻止派发。已派发时，记录取消意图，执行器接到后中断原消息；中断或停止得到确认才写终态。 | 取消命令按 messageId 重复提交时复用结果。失联或 Docker 状态未知时，该会话保持待核对。 |
| 收尾 | 所有事件、结果、续租及终态写入都校验当前代次，并与状态在同一事务提交。按会话行、消息行的固定顺序加锁。 | 迟到事件被拒绝。仅在操作可安全重试时重试数据库事务。数据库连不上与单事务冲突分别处理。 |

排队可用原有 `accepted` 展示，领取可以先只表现为租约元数据。数据库时钟作为租约基准。首版轮询做可靠兜底，后续可用 PostgreSQL 通知缩短等待。具体轮询间隔、心跳、租约和容量按隔离压测确定。

## 旧执行器如何失去写入权

租约过期表示失联。执行代次只能拦数据库写入和经受管网关的请求。容器可能仍持有工作目录并继续写入。接手必须同时满足：

1. 拿到持久工作区对应的会话文件锁。
2. 对正确的 Docker 引擎按实例和会话标签枚举旧容器。确认所有旧容器已停止并清理，旧执行凭据失效。
3. 当前执行代次仍有效且未取消，才允许新 Runner 写入。持锁贯穿本轮执行及收尾。

引擎状态未知时冻结该会话，保留原因和可重试核对记录，其他会话继续接单。原有同一 Runner 的正常下一轮可以按现有协议复用，崩溃后的新写入者仍遵循上述规则。多主机阶段要解决旧主机仍能写共享存储的问题，届时另验存储侧的写入撤销或单写挂载。

## 模型调用和扣费

一次 Agent 任务可以合法调用模型多次。给每次逻辑调用生成稳定的 `callId`，由受信 Runner 传输层提供，限定到消息、执行代次和调用序号。同一次传输重试沿用该 ID，模型的下一次实际调用使用新 ID。用请求正文哈希做冲突检测，避免把正文相同的两次正常调用合并。

受管推理网关先校验运行代次和凭据，写唯一调用记录与钱包预占，再授权一次上游发送。正式实现须把调用记录、预占和关联 ID 在一个事务里提交，再发起外部请求。模型侧接收请求与本地事务之间存在不可原子提交的窗口。提交发送意图后，遇到断网、响应缺失或代理崩溃，保留同一请求及预占为待核对，只有上游明确未受理或提供经验证的幂等协议时才可自动重发。已经完成的重复请求可返回缓存结果或明确的已完成状态，继续使用原结算记录。

现有钱包以请求 ID 对重复结算去重。生产接入应复用该逻辑，并在创建钱包请求之前拦同一个 `callId`。恢复保留既有平台承担明确用户中断未知费用的规则，服务故障未知与正常取消须有可区分的证据。需要用固定原生 SDK 和 LiteLLM 实测稳定调用 ID 是否跨传输重试保持，以及实际生效的重试和回退配置。若供应商不支持幂等，只能保证 Harbor 对未知结果不自动重放，无法仅靠数据库证明上游没有执行或没有产生费用。

## 接入顺序与发布门槛

1. 修正同一会话锁顺序，增加可独立验证的接单、领取、取消、派发授权和代次写入入口。只让新增队列行进入新执行路径。
2. 将执行循环接回现有原生 Runner，启用每会话核对和当前代次校验。先在一个主机上跑通 HTTP 202、SSE、取消、进程崩溃和会话恢复。把应用开发和分析的同步等待改为查询持久状态后再迁移。
3. 接入受管推理的稳定调用 ID 和原子预占，补上 SDK、网关与工作区共同失效验证。用计数型模型替身逐个切断响应，再验证真实供应商的幂等或不可自动重发口径。
4. 在目标 Linux 验证 API 崩溃、执行器崩溃、旧容器继续写、Docker 不可查、取消竞态、上游响应丢失和结算回执重复。只有按实际请求链全部通过才开启托管队列。

[可复跑的故障探针](../../tests/queue-fault-probe.mjs)调用真实 Harbor 的接单、取消、Docker 后端、推理代理与钱包方法。候选 SQL 只在临时测试 schema 中执行。探针保留了真实故障对照，不替代队列接入后的端到端验收。

复跑需要先构建项目，然后设置 `AH_TEST_DATABASE_URL` 指向本机专用空库 `harbor_queue_probe`，运行 `node tests/queue-fault-probe.mjs`。Docker 需已有 `postgres:18-alpine`，或通过 `AH_QUEUE_PROBE_IMAGE` 指定本机已有的带 POSIX shell 镜像。探针仅访问本机模型替身。

## 2026-11-06 实测判定

- 真实 PostgreSQL 18 与两处进程 SIGKILL。接单提交后、执行尚未开始时进程死亡，原请求可重查，八个并发领取者只取得一份任务。领取后取消先提交时，派发被拒绝，重复取消只记录一次。
- 真实 Docker 容器绑定临时目录持续写入。数据库旧代次已拒绝且租约已过期时，容器仍能写文件。Docker 查询故障时禁止派发，确认停止和清除后才允许派发。
- 本地模型替身收到请求后故意不回包，再杀进程。原型中的重复调用被拦，过期已派发任务不重新领取，钱包保留待核对且本地扣费为零。有完整用量时，两个同 ID 的请求只转发一次，重复结算只产生一笔扣费。
- 现有推理代理的对照组用同一个正文先后发两次 HTTP 请求，上游收到两次、钱包产生两笔。它证明当前接口缺少稳定调用 ID，不能据此推断原生 SDK 已经在自动重发。
- 原型用于验证边界。正式的调用记录与钱包预占合并事务、HTTP 接单到原生 Runner 的集成、SDK 重试与真模型均待验证。
