# Migration

当前品牌、npm包名和Docker镜像前缀统一为`agent-harbor`，配置统一为`AH_*`。已有部署升级时需要同步配置和重建镜像。

- 模型凭证没有内置有效值，复制`.env.example`并填写本地`.env`。
- 测试结果默认写入`var/evidence`，运行数据与用户会话不属于公开源码。
- 新的Docker项目标签为`io.agent-harbor.project=agent-harbor`，归属标签使用`harbor.*`。升级前应正常关闭旧CLI与容器；新命名规则不会自动接管旧标签下的环境。
- 数据根路径参与环境归属计算。迁移目录前先停止环境，不要在运行时直接移动数据根。
- 保留的原生会话受镜像内容ID保护。新镜像尚未验证兼容性时，请使用新会话ID，不删除保护字段或强行重放旧任务。
- chat每轮有独立attempt，但正常多轮可以共享一个容器。清理旧记录时，应先确认会话已关闭，并保留需要恢复的工作文件和原生状态。

## 版本 0.3.0 常驻Runner

chat正常多轮现在共享Runner和原生Claude进程；新增session.runnerId指向启动attempt，那里保存长期连接配置、stderr与runner-events.jsonl。连接凭证在整个环境关闭时清空，不能在每轮结束时清空启动文件。

新Keeper使用每次open独立的租约文件。先关闭旧CLI和容器，再构建0.3.0；旧0.2.0镜像保留。请同步本地AH_IMAGE为agent-harbor:0.3.0，用新会话ID开始；旧原生状态的跨镜像兼容性尚未验收，不删除imageId保护。

预算由逐轮query改为整段常驻query累计；错误后重建query会重新建立预算。租户硬配额和凭证自动续期尚未实现。

当前没有自动旧数据/旧镜像迁移工具。

## 版本 0.4.0 / v3 独立服务

默认npm run cli现在是HTTP客户端，旧直接执行入口为npm run cli:local。模块移动到src/service、clients、runtime、docker、agent和shared；导入路径与容器入口同步更新。

先关闭旧CLI和环境，保留v2镜像与数据。构建agent-harbor:0.4.0，在新数据根var/service-sessions生成开发访问密钥，单独启动npm run server。旧目录没有ownerId，不自动认领或公开；显式导入与跨镜像恢复兼容性尚未实现，不删除imageId检查。

服务模式退出CLI只断开；用户中断优先保留环境；关闭环境用close。原生中断可能保留后台进程，关闭环境才停止全部容器进程。服务崩溃后未完成消息标为interrupted，用户必须发送新的明确请求，不自动重放。

## V5到V6

在无运行任务/文件传输时停止旧服务，备份服务数据库及私有配置，再以原AH_DATA_DIR启动V6。会话ownerId保持，access-keys.json只在启动时导入；已撤销密钥不会重新生效。旧用户不按邮箱/同名自动关联外部身份。V6追加身份与用量表，不改执行镜像。

不要用V5直接打开已升级的生产数据根降级：旧版本只信任开发密钥文件，不理解V6撤销/停用记录。回退应停止服务并恢复升级前完整备份；不要与V6共用同一数据根并行运行。升级前历史费用不回填，旧会话首个新结果缺少基线时只记录观察值。

## V6到V7

无数据库/执行镜像升级。先停止无运行任务的旧服务、备份私有数据根，再运行npm ci与npm run build，以原AH_DATA_DIR启动。必须一起部署新版静态资源处理和Vite产物，不能仅替换旧服务的dist/web；保留原会话、草稿键和Cookie。

## SQLite迁移到PostgreSQL（已实现，生产切换未执行）

目标方案为PostgreSQL 18 + pg + Drizzle ORM/Kit。先保持单个执行服务和原`AH_DATA_DIR`，只迁移控制面数据库；不同时更换执行镜像、移动工作区或开启多实例。ORM负责表定义、查询类型与迁移生成，业务代码仍明确控制事务、锁和执行顺序。

PostgreSQL适配、迁移命令及导入脚本已实现；本节以下流程是切换时的操作约定。代码已不再使用SQLite，回退需要恢复旧版本与切换前备份，不能只改连接串。

### 先区分两种迁移

| 类型 | 用途 | 处理方式 |
| --- | --- | --- |
| 表结构迁移 | 在PostgreSQL建立/修改表、索引、约束 | Drizzle Kit生成SQL，审阅、测试后应用 |
| 业务数据迁移 | 把已有SQLite记录导入PostgreSQL | 单独导入脚本，保留原ID和业务状态 |

`drizzle-kit push`不用于生产直接同步结构。迁移作为受控部署步骤运行，不能让每个应用实例启动时自行争抢执行。表结构迁移不负责搬迁SQLite数据；代码回退也不等于数据库可以自动降级。

### 实现准备与演练

- 完成pg连接池、Drizzle schema及异步存储接口，连同调用方核对事务边界。
- 保留消息请求去重、每会话单活动消息、来源事件去重及会话内事件编号约束。额度检查/占用和状态/事件提交保持原子性。
- 使用当前数据副本，在独立测试库演练“建表→导入→核对→启动→回归”。记录源/目标版本、应用提交、备份位置及结果，不记录密钥明文。
- PostgreSQL的BIGINT、时间、布尔值、JSON等需要明确转换。保留现有毫秒时间戳、JSON内容和事件编号含义；不要由驱动默认返回类型悄悄改变API契约。
- 导入脚本检查源版本及目标状态；只向约定的空目标导入。按同一备份重跑必须有明确检测/恢复规则，不能靠覆盖写入掩盖部分成功。

### 命令与配置

```sh
npm run build
AH_DATABASE_URL=postgres://user:password@host:5432/agent_harbor npm run db:migrate
AH_DATABASE_URL=postgres://user:password@host:5432/agent_harbor \
  npm run db:import -- /path/to/control.sqlite --dry-run
AH_DATABASE_URL=postgres://user:password@host:5432/agent_harbor \
  npm run db:import -- /path/to/control.sqlite --report var/evidence/db-migration/2026-10-23/import.json
```

- `db:migrate`按文件名顺序应用`migrations/*.sql`，在`schema_migrations`记录名称、时间与校验值；已应用文件被改写会拒绝继续。服务启动不自动迁移，也不让多个实例争抢执行。
- `db:import`只读打开源库（会读取同目录WAL），要求`user_version=1`且九张表齐全；目标必须为空，导入在单个事务内完成，提交前核对各表行数与消息/事件外键，失败整体回滚。`--dry-run`只校验并打印数量。
- 重复执行按源库逻辑内容指纹识别：相同备份再次运行返回`already-imported`，不会覆盖或重复插入；不同内容的非空目标直接拒绝。
- `AH_DATABASE_POOL_MAX`控制连接池上限，默认10。连接串里的`options`会保留，服务另加语句超时与事务空闲超时。

演练通过后才能安排正式切换。

### 暂停写入与一致备份

1. 暂停新消息、新会话、上传及其他修改请求，等待现有任务和文件操作收尾。不要在仍能接收写入时开始导出。
2. 正常关闭该部署的执行环境，确认其容器已停止；保留单写入者与归属检查，不操作其他项目容器。未确认停止时中止切换。
3. 停止旧服务，确认旧进程退出并释放数据根锁。旧服务和新服务不能同时使用同一工作目录。
4. 备份SQLite、私有配置、工作区、原生Claude状态及恢复所需执行记录，保存文件清单和校验值。不能只备份数据库而遗漏成果与原生上下文。
5. SQLite使用WAL：采用正确的SQLite备份方式，或在正常关闭并确认数据库状态后做一致的离线备份；不能从运行中的数据库只复制`control.sqlite`，遗漏WAL里的提交。

备份及日志保持私有，不加入Git或源码包。

### 建表和导入

- 对空PostgreSQL目标应用已审阅的结构迁移，验证外键、唯一约束、部分唯一索引及迁移记录。
- 按外键顺序导入用户/身份、会话/消息/事件、登录与访问密钥、额度和用量等实际存在的数据；最终表清单以源版本为准，未实现的Skill表不虚构导入记录。
- 保留userId/ownerId、sessionId、messageId、clientMessageId、eventId、sourceEventKey及最后事件位置，不能重新生成这些业务ID。
- 原样保留账号停用、密钥撤销/到期、登录到期、取消/终态和费用观察基线。密钥仅迁移哈希；旧开发密钥配置不得使撤销凭证复活。
- 正式切换前应没有正常运行中的任务。遗留accepted/running/finalizing/reconciling等记录必须依据旧环境停止证据进入恢复流程，不得导入后自动重放。
- 目标导入失败时保持新服务未开放，先查明失败范围，不与原服务双写。

### 数据核对与功能验收

| 核对项 | 通过条件 |
| --- | --- |
| 记录完整性 | 各表行数、主键集合、关键字段及转换后的内容一致；无孤立外键 |
| 用户隔离 | 旧会话/文件仍属原用户；A不能读取B的会话、文件或未来个人技能 |
| 消息与事件 | 历史正文、终态、事件顺序、最后游标一致；无重复/遗漏 |
| 身份 | 新旧有效凭证按策略工作，停用/撤销/过期仍生效；若选择清除浏览器登录，应显式说明重新登录 |
| 文件与恢复 | 工作文件清单/校验值一致，下载正常；原生状态保留且遵守imageId兼容检查 |
| 并发规则 | 同一请求重复提交只接受一次，同会话并发冲突，跨会话额度不被并发绕过 |
| 控制与断线 | SSE补看、刷新、原生中断、关闭环境、服务故障恢复正常，不自动重放未知执行 |
| 数据库故障 | 不启动缺少提交证据的新任务；已提交但响应不明按原请求ID核对 |

在真实PostgreSQL上执行迁移与并发测试，不能以原SQLite测试通过替代。功能写入检查使用独立合成账号/会话，并记录这些写入；不向用户旧会话发送模型验证任务。

### 启动和开放

确认新服务连接PostgreSQL、沿用原数据根、执行镜像未变、就绪检查通过，随后开放请求。先小范围验证登录、历史、文件和一条受控任务，再观察数据库连接、错误、事件积压与存储容量。

持久性需要同时覆盖数据库备份恢复与工作文件/原生状态备份；托管数据库自动备份不能代替整套会话恢复演练。容器仍由单个执行服务管理，不因换库自动获得多节点接管能力。

### 失败回退

- **新服务尚未接受任何新写入**：停止新服务，确认没有新执行者；恢复匹配的旧版本与切换前完整数据/配置备份后启动旧服务。
- **新服务已经产生新写入**（包括测试登录、任务或其他写入）：不能直接切回旧SQLite，否则会丢失新状态。先暂停写入、保全PostgreSQL与文件现状，再修复新版本，或制定并验证反向数据迁移方案。不能用恢复旧备份宣称无损回退。
- 只有已证明兼容当前PostgreSQL结构的应用版本，才能作为不回退数据库的代码回滚目标；当前SQLite旧版不满足此条件。

切换失败不自动重放未知任务，不删除停止/归属保护字段，不将不确定状态标记为正常。

### 复核后的异步并发修复

接收阶段由单服务短锁保护：额度检查、消息提交与内存占位之间不再允许其他接收操作插入；文件传输、模型执行和模板复制仍在锁外。数据库事务先去重后判忙，取消固定原消息句柄；唯一冲突识别同时支持pg错误及Drizzle cause包装。导入的全部既定完整性指标非零时均回滚。

新增真实PG并发及异常导入回归后，共87项测试通过。此结果覆盖工程行为，不替代生产切换、备份恢复或真实模型业务验收。无需新增结构迁移；已有合法数据不重导，服务使用新版构建重启后生效。
